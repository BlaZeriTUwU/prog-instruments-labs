### Как читать замечания

Каждое замечание оформлено так: `### ID. Название (приоритет)`, потом место в коде, **Вид проблемы** и **Предложение** (с примером кода). Буквы в идентификаторах значат:

- **C**: критичные замечания (безопасность и корректность);
- **D**: дизайн и декомпозиция;
- **R**: читаемость;
- **P**: производительность и ресурсы;
- **T**: тесты и логирование.

Приоритеты: **критично** (неверный результат или уязвимость), **важно** (мешает развивать и тестировать код), **nit:** (мелкая придирка, исправлять необязательно, пишу «на будущее»).

## Критичные замечания: безопасность и корректность

Здесь шесть замечаний: два места, где программа, как мне кажется, даёт неверный результат (C5, C6), и четыре уязвимости или слабых места защиты (C1–C4).

### C1. SQL собирается из f-строк (критично как паттерн)

`bank.py:173, 194-201, 216-217, 232`. **Вид проблемы:** безопасность (SQL-инъекция). Значения подставляются прямо в текст запроса. Сейчас настоящей инъекции, думаю, нет: номер карты и PIN генерирует сама программа, сумма проходит через `int()`, а номер получателя сначала ищется в словаре `bank.cards`. Но защита держится на проверках, которые стоят в других местах и попали туда случайно. Стоит что-то поправить (скажем, добавить поиск по введённой строке), и уязвимость откроется. Ещё мелочь: двойные кавычки вокруг значений в SQLite означают имя колонки, и как строка текст читается лишь запасным вариантом, так делать не стоит.

**Предложение:** везде параметризованные запросы.

```python
c.execute("INSERT INTO card (number, pin) VALUES (?, ?)", (card_number, pin))
c.execute("UPDATE card SET balance = ? WHERE number = ?", (card.balance, card.card_number))
c.execute("DELETE FROM card WHERE number = ?", (card.card_number,))
```

### C2. PIN хранится открытым текстом (критично)

`bank.py:11, 173, 292`. **Вид проблемы:** безопасность. Строка 173 кладёт PIN в колонку `pin` как есть, а при входе (строка 292) программа просто сравнивает строки. Кто прочитает файл `card.s3db`, получит все PIN сразу.

**Предложение:** хранить соль и хеш, сравнивать через `hmac.compare_digest`. Показать PIN пользователю один раз при создании карты можно.

```python
import hashlib, hmac, os

def hash_pin(pin: str, salt: bytes) -> bytes:
    return hashlib.scrypt(pin.encode(), salt=salt, n=2**14, r=8, p=1)

salt = os.urandom(16)
c.execute("INSERT INTO card (number, pin_hash, salt) VALUES (?, ?, ?)",
          (number, hash_pin(pin, salt), salt))

hmac.compare_digest(hash_pin(entered, salt), stored_hash)
```

Есть оговорка: вариантов 4-значного PIN всего 10 000, так что от офлайн-перебора после утечки файла хеш не спасёт. По-настоящему здесь защищает ограничение попыток (C4).

### C3. Для PIN и номера карты используется `random` (критично)

`bank.py:111, 164`. **Вид проблемы:** безопасность. `random` работает на Mersenne Twister, это предсказуемый генератор, и для секретов он не подходит: зная достаточно предыдущих значений, можно вычислить следующие.

**Предложение:** модуль `secrets`.

```python
import secrets

pin = f"{secrets.randbelow(10_000):04d}"
can = f"{secrets.randbelow(10**9):09d}"
```

При этом исчезает длинная конструкция `''.join([str(random.choice(range(10))) for _ in range(4)])`.

### C4. Нет ограничения попыток ввода PIN, и по сообщению видно, есть ли карта (критично)

`bank.py:287-295`. **Вид проблемы:** безопасность (перебор и перечисление пользователей). В цикле входа нет ни счётчика, ни блокировки, ни задержки, так что все 10 000 вариантов PIN можно перебрать почти мгновенно. Кроме того, ответы разные: `Wrong card number!` для несуществующей карты и `Wrong pin to Credit Card!` для существующей. По ним можно подбирать номера и узнавать, какие карты зарегистрированы.

**Предложение:** одно сообщение об ошибке и блокировка после нескольких попыток. Счётчик лучше хранить в базе (колонка `failed_attempts`), иначе перезапуск программы его сбросит.

```python
MAX_ATTEMPTS = 3

if card is None or card.locked or not pin_ok(card, entered_pin):
    register_failed_attempt(card)          # +1, lock at MAX_ATTEMPTS
    print("Wrong card number or PIN!")
```

### C5. Перевод денег выполняется двумя отдельными `commit` (критично)

`bank.py:193-203`. **Вид проблемы:** логическая ошибка, нарушение атомарности. Списание с одной карты и зачисление на другую фиксируются двумя разными `commit`. Если программа упадёт между ними, деньги пропадут: у отправителя уже списано, а у получателя ещё не пришло. Баланс сначала меняется в памяти и только потом в базе, поэтому память и БД могут разойтись. А если одну базу откроют две копии программы, обе держат в памяти устаревший баланс и затирают изменения друг друга (потерянное обновление).

**Предложение:** одна транзакция, арифметику делает сама БД, а хватает ли денег, проверяется прямо в запросе.

```python
def transfer(conn, src: str, dst: str, amount: int) -> None:
    with conn:  # one transaction: commit on success, rollback on exception
        cur = conn.execute(
            "UPDATE card SET balance = balance - ? WHERE number = ? AND balance >= ?",
            (amount, src, amount),
        )
        if cur.rowcount != 1:
            raise InsufficientFunds
        conn.execute("UPDATE card SET balance = balance + ? WHERE number = ?", (amount, dst))
```

### C6. Большая сумма может молча стать дробным числом, нулевая сумма допускается (критично)

`bank.py:55, 186, 216-217`. **Вид проблемы:** логическая ошибка, переполнение. Сумма проходит через `int()`, а он принимает любые сколь угодно большие числа. Потом она попадает в SQL через f-строку, и, насколько я знаю по документации SQLite, целочисленный литерал, который не помещается в 64 бита, сохраняется как `REAL`. Тогда точность теряется: на очень больших суммах баланс превратится во что-то вроде `1e+30`. Ещё одна мелочь: проверка `income < 0` пропускает ноль (то же с `money < 0` в переводе), так что пополнение на 0 пройдёт с сообщением об успехе.

**Предложение:** сумма должна быть положительной и не больше верхней границы. Вместо f-строк нужны параметры (с ними Python сам бросит `OverflowError` на слишком большом числе), а ещё ограничение в схеме таблицы.

```python
MAX_AMOUNT = 10**9

if not 0 < amount <= MAX_AMOUNT:
    print("Please provide a number between 1 and 1 000 000 000.")
```

```sql
CREATE TABLE IF NOT EXISTS card (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    number TEXT NOT NULL UNIQUE,
    pin_hash BLOB NOT NULL,
    salt BLOB NOT NULL,
    balance INTEGER NOT NULL DEFAULT 0 CHECK (balance >= 0)
);
```

## Дизайн и декомпозиция

Главная беда в структуре: логика, ввод-вывод и работа с базой перемешаны, а состояние лежит в глобальных переменных. Из-за этого программу нельзя ни импортировать, ни нормально протестировать.

### D1. Программа запускается и открывает базу при импорте (важно)

`bank.py:4-12, 250-299`. **Вид проблемы:** побочные эффекты на уровне модуля. Соединение с `card.s3db` и главный цикл стоят прямо в теле файла, а не внутри функции. Значит, любой `import bank` создаст файл базы в текущей папке и сразу зайдёт в цикл с `input()`. Получается, что ни одну функцию не вызвать из теста или другого модуля, не запустив всё приложение целиком.

**Предложение:** вынести запуск в `main()` и создавать соединение там же.

```python
from contextlib import closing

DB_PATH = "card.s3db"

def main() -> None:
    with closing(sqlite3.connect(DB_PATH)) as conn:
        init_db(conn)
        run_menu(conn)

if __name__ == "__main__":
    main()
```

### D2. Глобальное состояние и скрытые зависимости (важно)

`bank.py:4, 6, 113, 223, 236, 250`. **Вид проблемы:** глобальные переменные, зависимости не видны в сигнатурах. Функции берут `conn`, `c` и `bank` из глобальной области, ничего не получая через аргументы. Например, `create_can` обращается к `bank`, который создаётся только на строке 250, ниже по файлу. Работает это лишь потому, что функцию вызывают позже. Плюс имена верхнего уровня `card`, `cards`, `card_number`, `user_input` совпадают с параметрами и локальными переменными в функциях, так что значение легко затенить по ошибке.

**Предложение:** передавать соединение и репозиторий явно.

```python
class CardRepository:
```

### D3. Ввод-вывод, бизнес-логика и SQL в одних функциях (важно)

`bank.py:42-60, 179-204, 207-247`. **Вид проблемы:** нарушение принципа единственной ответственности (SRP), уровни перемешаны. `CreditCard.add_income` читает ввод, проверяет сумму, меняет баланс и ещё печатает. `make_transfer` делает то же плюс два SQL-запроса, а `check_account` вдобавок ведёт меню. Из-за этого правила (какая сумма допустима, когда можно перевести деньги) невозможно проверить, не изображая клавиатуру.

**Предложение:** разделить на три слоя: меню (ввод-вывод), сервис (правила и исключения), репозиторий (SQL).

```python
class InvalidAmount(ValueError): ...
class InsufficientFunds(Exception): ...

def parse_amount(text: str) -> int:
    amount = int(text)                 # ValueError for non-numbers
    if not 0 < amount <= MAX_AMOUNT:
        raise InvalidAmount
    return amount

# menu layer
try:
    transfer(conn, card.number, target, parse_amount(input("Amount: ")))
except (ValueError, InvalidAmount):
    print("Please enter a valid amount.")
except InsufficientFunds:
    print("Not enough money!")
```

### D4. Два источника правды: словарь в памяти и база (важно)

`bank.py:63-87, 250-264`. **Вид проблемы:** дублирование данных, можно получить рассинхронизацию. Все карты сначала читаются из БД в `Bank.cards` и `Bank.cards_can`, а потом каждое изменение делается дважды: в объекте и в SQL. Класс `Bank` по сути пустой, это обёртка над словарём. Если запись в БД не удалась (см. C5) или базу трогает другой процесс, память и файл разойдутся, а баланс будет браться из устаревшей копии.

**Предложение:** оставить один источник данных, базу. Баланс читать и менять SQL-запросами, `CreditCard` создавать по запросу, а `Bank` удалить. Уникальность номера обеспечить через `UNIQUE` (см. C6) и повтор генерации при конфликте.

```python
def find_card(conn, number: str) -> CreditCard | None:
    row = conn.execute(
        "SELECT number, balance FROM card WHERE number = ?", (number,)
    ).fetchone()
    return CreditCard(*row) if row else None
```

`bank.py:207-247`. **Вид проблемы:** высокая цикломатическая сложность, длинная цепочка `if/elif`. В функции 41 строка, цикл и шесть веток; по моему подсчёту ветвлений сложность выходит около 10. Одна из веток ещё и содержит вложенные проверки с SQL.

**Предложение:** каждое действие в свою функцию, а выбор делать через словарь.

### D6. nit: `quit()` и соединение с БД никогда не закрывается

`bank.py:245`. **Вид проблемы:** нестандартный выход, утечка ресурса. `quit()` добавляет модуль `site` для интерактивной консоли, в программах на него полагаться нельзя (например, при запуске с `python -S` его нет). ## Читаемость

Читать код местами труднее, чем нужно: алгоритм Луна написан мудрено, проверки повторяются, а имена и константы не следуют PEP 8. Форматирование и кавычки здесь не разбираю, это работа форматтера.

### R1. nit: имена в верхнем регистре внутри функций

`bank.py:111-114, 118-130, 153-156`. **Вид проблемы:** нарушение PEP 8. Внутри функций встречаются `CAN`, `CAN_list`, `BIN`, `BIN_dict`, `BIN_list`, `IIN`, хотя имена в верхнем регистре принято оставлять для констант. Курсор базы назван `c`, а параметр `BIN` в `create_check_sum` на самом деле держит 15 цифр, то есть IIN плюс CAN, так что имя ещё и вводит в заблуждение.

**Предложение:** `snake_case` и нормальные имена.

| Было | Стало |
| --- | --- |
| `c` | `cursor` |
| `CAN`, `CAN_list` | `can`, `can_digits` |
| `BIN`, `IIN` | `payload`, `iin` |
| `BIN_dict`, `BIN_list` | убрать (см. R2) |

### R2. Контрольная цифра считается сложнее, чем нужно (важно)

`bank.py:118-140`. **Вид проблемы:** излишняя сложность, нечитаемость. Алгоритм Луна здесь разбит на два словаря, два списка и преобразование суммы в строку (`int(str(sum_all)[-1])`, потом ещё `if num == 0`). Судя по коду, работает он верно, но понять это с первого раза трудно, а комментарии просто пересказывают код русскими словами.

**Предложение:** я бы сделал один цикл и одну строку с арифметикой.

```python
def luhn_check_digit(payload: str) -> str:
    total = 0
    for i, ch in enumerate(payload):
        digit = int(ch)
        if i % 2 == 0:  # 1st, 3rd, ... digits of a 16-digit number are doubled
            digit *= 2
            if digit > 9:
                digit -= 9
        total += digit
    return str((10 - total % 10) % 10)
```

## Производительность и ресурсы

Для учебной программы с десятком карт проблем нет. Но кое-что растёт вместе с числом карт, и это видно прямо по коду. Замеров я не делал, пишу по структуре программы.

### P1. Все карты загружаются в память при каждом запуске (важно при росте)

`bank.py:254-264`. **Вид проблемы:** алгоритмическая эффективность, расход памяти. При старте программа читает всю таблицу `card` в словарь `Bank.cards`, хотя за одну сессию нужна одна-две карты. Время старта и память растут линейно с числом карт. Ещё мне не нравится `SELECT *` вместе с `tup[1]`, `tup[2]`, `tup[3]`: всё держится на порядке колонок. Добавишь в таблицу поле (например, `pin_hash` из C2), и разбор тихо сломается.
